# Team Working Agreement

## Project

Complaint Resolution System

## Purpose

This agreement defines how the team will collaborate during the six-week project to ensure consistent communication, quality delivery, and timely resolution of issues.

---

## Team Roles

| Role | Responsibilities |
|---|---|
| Product Owner | Defines requirements, priorities, and acceptance criteria |
| Scrum Master / Team Lead | Facilitates ceremonies, removes blockers, and tracks progress |
| Developers | Design, develop, test, and review code |
| QA/Test Engineer | Validates functionality and quality requirements |
| All Team Members | Participate in planning, stand-ups, reviews, and retrospectives |

---

## Working Hours

- Core collaboration hours: 9:00 AM–5:30 PM.
- Team members should be available during core hours.
- Planned absences should be communicated in advance.
- Items requiring schedule flexibility will be acknowledged within the same working day.

---

## Daily Stand-Up

### Schedule

- Daily at 9:30 AM.
- Duration: 15 minutes maximum.

### Format

Each member answers:

1. What did I complete yesterday?
2. What will I work on today?
3. Do I have any blockers?

### Rules

- Keep updates concise.
- Take detailed discussions offline after the stand-up.
- Blockers should be raised immediately.

---

## Branch Naming Convention

All work must be completed on feature branches.

**Format:** `feature/<description>`

**Examples:**

- `feature/101-complaint-creation`
- `feature/102-status-update`
- `bugfix/15-validation-error`
- `hotfix/201-production-fix`

Branch names should be lowercase and use hyphens.

---

## Pull Request (PR) Expectations

### Before Creating a PR

- Code compiles successfully.
- Unit tests pass.
- Linting issues are resolved.
- Documentation is updated if applicable.

### PR Requirements

- Include a clear title and description.
- Reference the associated ticket or story.
- Include screenshots or test output if changes affect the UI.
- Keep PRs small and focused.

---

## Code Review Expectations

- A minimum of one reviewer approval is required.
- Reviews should be constructive and actionable.
- The author should respond to all comments.

### Review Turnaround Time

| Priority | Target Review Time |
|---|---|
| Standard PR | Within 24 hours |
| Critical Bug Fix | Within 4 hours |

---

## Definition of Done

A task is complete when:

- Development is completed.
- Unit tests pass.
- Code is reviewed and approved.
- Documentation is updated.
- Acceptance criteria are satisfied.
- Changes are merged into the `main` branch.

---

## Blocker Escalation Process

### Step 1

Raise the blocker during stand-up or in team chat.

### Step 2

If unresolved for more than 4 hours, notify the Team Lead/Scrum Master.

### Step 3

If unresolved for more than one business day, escalate to the Product Owner or Project Manager.

### Step 4

Document the resolution and lessons learned.
